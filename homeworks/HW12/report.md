# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- **Датасет:** `S12-hw-dataset.csv` — часовой временной ряд с 01.01.2025 по 29.06.2025 (4320 наблюдений).
- **Прогнозировалось:** значение колонки `target` на 1 шаг вперёд (на 1 час).
- **Разбиение:** `train / validation / test = 60% / 20% / 20%` по времени (chronological split).
- **Сравнивались подходы:**
  - `B1`: Naive Last (прогноз = последнее известное значение)
  - `B2`: Moving Average с окном 24 часа
  - `B3`: Ridge-регрессия на лаговых, rolling и календарных признаках
  - `R1`: GRU-сеть на оконном представлении (window_size=24)
- **Лучший подход:** `R1 (GRU)` — показал наименьшие ошибки на валидации благодаря способности улавливать нелинейные временные зависимости.

## 3. Данные и постановка задачи

- **Датасет:** `S12-hw-dataset.csv`
- **Целевая колонка:** `target` (непрерывная числовая переменная)
- **Частота временного ряда:** часовая (24 значения в сутки)
- **Горизонт прогноза:** 1 шаг вперёд (1 час)
- **Размер датасета:** 4320 наблюдений
- **Диапазон дат:** 2025-01-01 00:00 — 2025-06-29 23:00
- **Есть ли дополнительные внешние признаки:** нет, только `date` и `target`

> **Комментарий:** Ряд демонстрирует выраженный **восходящий тренд** и **суточную сезонность** (пики в дневные часы, спады ночью). Пропуски отсутствуют, выбросы минимальны. Основная сложность — предсказать краткосрочные колебания на фоне тренда, что требует учёта как локальных паттернов, так и долгосрочной динамики.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- **Как выполнен split:** данные отсортированы по `date`, затем разделены последовательно: первые 60% — train, следующие 20% — validation, последние 20% — test.
- **Доли:** `train=2592`, `val=864`, `test=864` наблюдения.
- **Почему random split некорректен:** временные ряды обладают автокорреляцией — будущие значения зависят от прошлых. Случайное перемешивание создаёт утечку информации из будущего в обучающую выборку, что приводит к завышенным метрикам и неадекватной оценке модели на реальных данных.

### 4.2. Признаки для baseline-моделей

- **Лаги:** `[1, 2, 3, 6, 12, 24]` часов — через `.shift(lag)` с обязательным сдвигом на 1, чтобы избежать утечки.
- **Rolling-признаки:** `mean`, `std`, `min`, `max` с окном 24 часа, вычисляемые на сдвинутых данных (`.shift(1).rolling(24)`).
- **Календарные признаки:** `hour`, `day_of_week`, `is_weekend`, а также циклическое кодирование часа (`hour_sin`, `hour_cos`).
- **Обработка пропусков:** после создания лагов и rolling-признаков строки с NaN удаляются через `.dropna()`.
- **Масштабирование:** `StandardScaler` обучался **только на train**, затем применён к val и test для предотвращения утечки.

## 5. Модели и эксперименты (B1, B2, B3, R1)

| Модель | Описание |
|--------|----------|
| **B1** (`naive-last`) | Прогноз = значение `target` в предыдущий час. Нулевая сложность, базовый ориентир. |
| **B2** (`moving-average`) | Прогноз = среднее за последние 24 часа. Сглаживает шум, учитывает суточную сезонность. |
| **B3** (`ridge-lag-features`) | Линейная регрессия с L2-регуляризацией на наборе лаговых, rolling и календарных признаков. |
| **R1** (`gru-forecast`) | Двухслойная GRU-сеть (hidden_size=64) на последовательностях длины 24, обучается через MSE-loss. |

**Дополнительно:**
- **Основная метрика выбора:** `MAE` (Mean Absolute Error) — интерпретируема, устойчива к выбросам.
- **Дополнительные метрики:** `RMSE`, `MAPE`.
- **`window_size` для GRU:** `24` (соответствует суточному циклу).
- **Batch size:** `64`
- **Максимальное число эпох:** `50`
- **Optimizer:** `Adam(lr=1e-3, weight_decay=1e-5)`
- **Learning rate scheduler:** `ReduceLROnPlateau` (factor=0.5, patience=5)
- **Сохранение лучшей модели:** чекпоинт по минимальному `val_MAE` через `torch.save()`.

## 7. Анализ

1. **Naive baseline (B1)** оказался слабым, так как не учитывает ни тренд, ни сезонность — прогноз «вчерашнего часа» не отражает суточных колебаний.
2. **Moving Average (B2)** улучшил результат за счёт сглаживания шума и учёта суточного цикла, но «запаздывает» при резких изменениях.
3. **Ridge на признаках (B3)** превзошла B1/B2, потому что лаги и rolling-статистики явно кодируют локальную динамику, а регуляризация предотвращает переобучение.
4. **GRU (R1)** дала наилучший результат: рекуррентная архитектура автоматически извлекает сложные временные паттерны, которые трудно задать вручную.
5. **Тренд и сезонность** явно видны на графиках: ряд растёт в долгосрочной перспективе, а внутри суток наблюдаются пики днём. Модель, не учитывающая это, систематически ошибается.
6. **Утечки данных** могли возникнуть при: (а) использовании `.shift(0)` вместо `.shift(1)` для лагов; (б) обучении scaler на всём датасете; (в) случайном перемешивании перед split.
7. **Выбор по validation, а не test** принципиален: test — это «экзамен», его можно использовать только один раз для финальной оценки, иначе возникает риск подгонки под тест.
8. **Наиболее показательные ошибки**: модель хуже предсказывает резкие скачки (например, в выходные), что указывает на возможность улучшения через добавление внешних признаков (праздники, погода).

## 8. Итоговый вывод

- **Базовый подход для такой задачи:** `Ridge на лаговых признаках` — прост в реализации, интерпретируем, даёт хороший результат при ограниченных данных.
- **Когда достаточно простого baseline:** если ряд стационарен, сезонность слабая, а требования к точности умеренные.
- **Когда переходить к GRU/нейросетям:** при наличии сложных нелинейных зависимостей, длинной истории, больших объёмах данных и высоких требованиях к точности.
- **Главный урок по валидации:** для временных рядов критически важно сохранять хронологический порядок при разбиении и никогда не «заглядывать в будущее» при создании признаков.
